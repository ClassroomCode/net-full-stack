.NET Runtime and SDK

Runtime

Applications built for the .NET platform run in a managed execution environment. This means that a compatible version of the .NET Runtime must be installed on any host where the code will execute.

Every .NET language (C#, F#, etc.) is compiled into CPU-agnostic Intermediate Language (IL) code that is Just-In-Time (JIT) compiled into native machine code by the .NET runtime. This architecture is similar to how Java code is compiled into bytecode that is JIT compiled into native code at runtime by the Java Virtual Machine (JVM).

Many tools exist that allow you to view the IL code produced by the C# compiler. One free online tool is sharplab.io. Given a snippet of C#, SharpLab can be used to view the "lowered" C#, the IL code, and even the native x86 assembly. SharpLab will be used to explore some features of C# that are covered later in this course.

It is possible to publish an app using Native AOT deployment. This produces a self-contained app that has been ahead-of-time (AOT) compiled to native code. These apps can run on machines that do not have the .NET runtime installed. Native AOT has some limitations and should only be used in specific scenarios. Refer to the documentation for more information.

Different versions of the .NET Runtime can be downloaded and installed for running different types of .NET applications:

  • .NET Runtime: Components needed to run a console app

  • .NET Desktop Runtime: Everything in the .NET Runtime plus additional components for running desktop Windows applications

  • ASP.NET Core Runtime: Everything in the .NET Runtime plus additional components for running web/server applications

You can check which versions of the runtime are currently installed on a machine via the command line.

Command to display the list of installed runtimes
$ dotnet --list-runtimes
Sample output on macOS
Microsoft.AspNetCore.App 10.0.1 [/usr/local/share/dotnet/shared/Microsoft.AspNetCore.App]
Microsoft.NETCore.App 10.0.1 [/usr/local/share/dotnet/shared/Microsoft.NETCore.App]

The version of the runtime required by an application is determined by the target framework moniker (TFM) in the app’s project file.

TFM for an app that requires version 10.0 of the runtime
<TargetFramework>net10.0</TargetFramework>

Runtime Version Roll-Forward

When running a framework-dependant application, the app host will use the latest patch version of the runtime with the same major/minor version number as the TFM. For example, if the TFM specifies net10.0 and the machine has version 10.0.0 and 10.0.1 of the runtime installed, the host will use the 10.0.1 version. In this scenario, 10.0.1 will be used even if a newer minor version (e.g., 10.1.0) is also installed.

If a runtime with the same major/minor version as the TFM is not installed, the app host will use the newest minor version of the runtime with the same major version. For example, if the TFM specifies net10.0 but 10.1.0 is the only runtime installed, the host will use that version of the runtime. This is referred to as "minor version roll-forward".

If an app with a TFM of net10.0 is using the 10.1.0 version of the runtime because of minor version roll-forward, later installing a version such as 10.0.2 will cause the app host to select the older version of the runtime on subsequent runs.

The roll-forward behavior for an app can be explicitly specified in the app’s project file, in the *.runtimeconfig.json file, or on the command-line when the app is launched.

Project file
<PropertyGroup>
  <RollForward>LatestMinor</RollForward>
</PropertyGroup>
*.runtimeconfig.json
{
  "runtimeOptions": {
    "rollForward": "LatestMinor"
  }
}
Command-line
$ dotnet myapp.dll --roll-forward LatestMinor

Refer to the documentation for information about the other possible values for the roll-forward setting and when they should be used.

When performing a self-contained deployment, a specific version of the runtime is selected during the publishing process. The selected version of the runtime is bundled with the app and that is the version that will always be used.

Runtime Package Store

Each version of the .NET Runtime also includes a collection of NuGet packages commonly used by the type of app supported by the runtime (console, desktop, or Web). These packages are implicitly referenced based on the Sdk attribute in app’s project file.

Project file for a Web project
<Project Sdk="Microsoft.NET.Sdk.Web">

For a Web app in .NET 10, this includes over 300 individual packages. These packages are not deployed with the app since the build tools know these packages are provided as part of the runtime. This approach results in faster deployments, lower disk space usage, and improved startup performance.

Any NuGet package or .NET assembly that your project references that is not part of the runtime package store must be deployed to the target environment along with your app. Fortunately, the .NET build tools copy any such dependencies into the output directory automatically whenever the app is built.

SDK

Each version of the .NET Runtime only contains the components necessary to run a specific type of .NET app (console, desktop, or Web). This helps to reduce the overall size of an app deployment. On the other hand, the .NET SDK includes all three variants of the runtime and all the additional components needed to build and debug a .NET app.

The .NET SDK includes the .NET command-line interface (CLI). The CLI includes dozens of commands including build, run, test, and publish. When combined with a text editor, the CLI provides everything needed to develop, test, debug, and deploy a .NET app.

Rather than use a basic text editor and CLI commands, most .NET developers prefer to use a more full-featured IDE like Microsoft Visual Studio or JetBrains Rider. However, these different IDEs all use the same CLI commands and project templates that are provided by the .NET SDK.

global.json

By default, the CLI will use the newest version of the SDK installed on the machine. Microsoft recommends always using the newest version of the SDK even if you need to target an older version of the .NET Runtime (supported via the TFM in the project file).

If necessary, it is possible to explicitly specify the version of the SDK that should be used by having a global.json file.

Example global.json file
{
  "sdk": {
    "version": "9.0.305"
  }
}

When this file is present, it will cause any SDK commands executed in this directory (or within any subdirectory) to use the specified version of the SDK.

If the specified version of the SDK is not available on the machine, an error will be generated and the user will be prompted to install the version specified.

Having a global.json file in a project’s source control repository can help enforce consistency for all the members of a development team. Although .NET makes it easy for each team member to use their preferred development environment (VS Code, Rider, etc.), it is a best practice to have everyone working on a project using the same version of the .NET SDK.
