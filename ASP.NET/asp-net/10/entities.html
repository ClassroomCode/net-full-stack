Entities

The Northwind sample database includes 13 tables with information about customers, employees, order, products, suppliers, and more. The AddressBook API will provide a way to retrieve and modify information about customers. The Customers table in the database has the following columns:

  • CustomerID (PK, nchar(5), not null)

  • CompanyName (nvarchar(40), not null)

  • ContactName (nvarchar(30), null)

  • ContactTitle (nvarchar(30), null)

  • Address (nvarchar(60), null)

  • City (nvarchar(15), null)

  • Region (nvarchar(15), null)

  • PostalCode (nvarchar(10), null)

  • Country (nvarchar(15), null)

  • Phone (nvarchar(24), null)

  • Fax (nvarchar(24), null)

To work with this data, we will need to define a C# type that matches the shape of the database table.

The SQL Server nchar type represents a fixed-length Unicode string while the nvarchar type represents a variable-length Unicode string (with a maximum size specified). Both of these can be represented in C# by the standard .NET String type.

Customer class

  1. Add a new folder to the AddressBook.API project named Entities.

  2. Add a new class to the Entities folder named Customer.

  3. Define an automatically implemented property for each column shown in the list above. Use a nullable type for a column that allows for a null value.

    public class Customer {
  public string CustomerID { get; set; } = string.Empty;
  public string CompanyName { get; set; } = string.Empty;
  public string? ContactName { get; set; }
  public string? ContactTitle { get; set; }
  public string? Address { get; set; }
  public string? City { get; set; }
  public string? Region { get; set; }
  public string? PostalCode { get; set; }
  public string? Country { get; set; }
  public string? Phone { get; set; }
  public string? Fax { get; set; }
}

    Although we are not using them here, tools exist that can scaffold entity type classes based on an existing database schema. Refer to the documentation for more information.

    This class is defined so that it’s property names exactly match the database table names but this is not required. If a property name does not match it’s associated column name, some additional code (or configuration) is required. This will be covered in a future section.

  4. Save the file and build the solution (Build  Build Solution) to check for any compiler errors.

Data Access

At this point, you could use ADO.NET to perform low-level data access. To do this, you would create a connection to the database, define a command, execute the command, and map the data returned into an instance of the appropriate type.

using var conn = new SqlConnection(connectionString);
conn.Open();
SqlCommand cmd = new() {
  Connection = conn;
  CommandText = "SELECT * FROM Customers";
};
SqlDataReader rdr = cmd.ExecuteReader();
var customers = new List<Customer>();
while (rdr.Read()) {
  customers.Add(new Product {
    CustomerID = rdr.GetString(0),
    CompanyName = rdr.GetString(1),
    // map the remaining fields
  });
}

This method of data access provides low-level control but also requires a large amount of repetitive boilerplate code. Therefore, a higher-level object-relational mapping (ORM) framework is often used instead. The most popular ORM for modern .NET applications is Microsoft’s Entity Framework Core (EF Core).

Although EF Core is a very powerful and mature framework, there are still times when it might make sense to use ADO.NET. One example would be an old, poorly designed database. In a scenario where the database does not adhere to good relational database design principles, it can be difficult to configure EF Core to work with it. Ideally, in this scenario, the database design should be improved but you may not always have that option.
