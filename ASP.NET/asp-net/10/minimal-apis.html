Minimal APIs

Minimal APIs are architected to create HTTP APIs with minimal dependencies. They’re ideal for microservices and apps that want to include only the minimum files, features, and dependencies.

Minimal APIs are discussed in this section while controller-based APIs are covered in a different section.

REST Principles

When designing endpoints for a modern Web API, it is recommended to follow some basic REST principles. Some of these principals include:

  • Use the most appropriate HTTP method for the action being performed (GET, POST, PATCH, etc.)

  • Clean, extension-less URIs that identify resources (/products/6 instead of /products.aspx?id=6)

  • Query strings that are used to provide extra information that may affect the presentation but that are not required to identify the resource being acted on (/products/dairy?sort=price instead of /products?cat=dairy&sort=price)

Route Endpoints

The app’s existing terminal middleware returns the same response regardless of the URL or HTTP method but there are extension methods on the WebApplication type for creating a more specific endpoints. The most commonly used correspond to the different HTTP methods (MapGet, MapPost, MapPut, MapPatch, and MapDelete).

A route endpoint consists of two things:

  • Route pattern: Used to match against the URL of the incoming request to determine if the endpoint handler should be executed. The is also commonly referred to as a route template.

  • Handler: The delegate used to process the request if the URL matches the specified pattern.

Here is an example of how to define an endpoint that will return the string "Hello, World!" if a GET request is made for the app root:

app.MapGet("/", () => "Hello World!");

If the system is unable to find an endpoint that matches the incoming request, an HTTP 404 (Not Found) response will be returned.

Retrieval endpoint

  1. Replace the existing terminal middleware with a root endpoint (GET) that returns all of the customers.

    app.MapGet("/customer", () => {
  using var db = new NorthwindContext();
  var customers = db.Customers.ToList();
  return customers;
});

  2. Run the app, make a request for http://localhost:5000/customer, and notice that the system automatically serialized the list of customers into JSON.

  3. Stop the app.

Route Value Parameters

A route template string can include route value parameters that act as named placeholders in the URL. The endpoint handler can accept these as incoming parameters to the function.

app.MapGet("/customer/{id}", (string id) =>
    $"Customer requested with an id of {id}");

In this example, id is a required parameter. If a value is not present in that position in the URL then the route will not be considered a match.

If appropriate, a route value parameter can be identified as optional:

app.MapGet("/customer/{id?}", (string? id) =>
    $"Customer requested with an id of {id}");

If a request is made for /customer, this route will be considered a match and the value of id will be null.

Retrieval of an individual customer

  1. A new endpoint that allows for the retrieval of an individual customer based on the customer’s ID.

    app.MapGet("/customer/{id}", (string id) => {
    using var db = new NorthwindContext();
    var customer = db.Customers.Find(id);
    return customer;
});

    There are several different LINQ extension methods for retrieving a single entity (First, FirstOrDefault, Single, SingleOrDefault, and Find). In this case Find is the best fit because it is designed specifically for retrieving an entity based on its primary key value.

  2. Run the app and make a request for http://localhost:5000/customer/greal. One customer should be returned.

  3. Make another request for a customer that does not exist (e.g., http://localhost:5000/customer/xxx). What is the response?

  4. Modify the endpoint to return a more appropriate response (404) for when a customer cannot be found. In addition to the conditional check, you will also need to modify the return statement so that the return type of the lambda expression is consistent.

    if (customer is null) return Results.NotFound();
return Results.Ok(customer);

  5. Test the modified endpoint and confirm that a 404 is returned.

Testing APIs

Sometimes, a web browser is enough to test an API endpoint (GET request). However, many other endpoints will require a different HTTP client to properly test them. There are several HTTP clients that are popular among ASP.NET Core developers:

  • Visual Studio with .http files

  • HttpRepl

  • Postman

  • Bruno

  • Insomnia

  • REST Client extension for VS Code

Visual Studio and .http Files

A file with a .http or .rest extension can be added to an ASP.NET project. Visual Studio will recognize the file and provide features for testing your API.

Test an API

  1. Add a new file to the project named tests.http

  2. Add a line to the file for retrieving all of the customers.

    GET http://localhost:5000/customer

  3. Ensure the app is running and then click "Send Request" in Visual Studio.

  4. Do the same for requests to retrieve an individual customer. Separate requests with a delimiter as shown below.

    GET http://localhost:5000/customer/greal

###

GET http://localhost:5000/customer/xxx

  5. Test the behavior of each.

  6. Stop the app.

It is also possible to include a message body when using other HTTP methods (e.g., POST). We will use that functionality later on.

Route Constraints

There can be a situation where an incoming URL might match the pattern defined by two different endpoints.

app.MapGet("/blog/{cat}/{subcat}/{topic}", ...)
app.MapGet("/blog/{year}/{month}/{day}", ...)

In this example, a request for /blog/2024/06/15 would be considered a match for both endpoints and this would result in an AmbiguousMatchException.

Route constraints can be used to define additional conditions as part of the pattern that must be met before an endpoint is considered a match.

app.MapGet("/blog/{year:int}/{month:int}/{day:int}", ...)

This endpoint will only be considered a match if every route value parameter is a valid int. Refer to the documentation for a list of other route constraint types.

The purpose of route constraints is to help the routing system differentiate between routes that would otherwise be ambiguous. It is NOT designed to be used for input validation. Attempting to use route constraints for input validation can result in validation logic that…​

  • Is difficult to debug

  • Is not executed when executing automated unit tests

  • Returns the incorrect HTTP status code (404 vs. 400)

For the example above, the implementation of the date-based endpoint should include validation code to confirm the provided values represent a valid date and that a blog article exists for that date.
