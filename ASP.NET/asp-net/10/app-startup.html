App Startup

For an ASP.NET Core web app, there are several things that must happen before the app is ready to respond to incoming HTTP requests. This includes initializing an HTTP server and configuring a request processing pipeline. Before we work on those aspects, we will learn about how .NET knows where to find our startup code.

Entry Point

Every .NET must have a method that serves as its entry point (first code to be run). The .NET runtime requires that the entry point method be named Main. By convention, this method is defined as a member of a class named Program in a file named Program.cs but the use of the name "Program" is not required.

class Program
{
    static void Main(string[] args) { ... }
}

Although uncommon, it is possible to have an app with more than one method named Main. However, in that case, one of the methods must be identified as the entry point via a compiler option.

Top-Level Statements

First introduced in .NET 6, the C# compiler supports a feature called top-level statements. When compiling a .NET project, if the compiler detects executable code outside of any type (i.e., at the "top-level"), it will automatically generate a Main method and move the top-level code into that method.

The SDK project templates are now configured to use this feature by default (Program.cs file will contain top-level statements) but this can be disabled by using the --use-program-main CLI option.

dotnet new web -n MyApp --use-program-main

Visual Studio and Rider also provide this option via a checkbox when creating a new project.

Entry Point

  1. Use your preferred text editor to create a new file.

  2. Add a top-level statement.

    Console.WriteLine("Hello, World!");

  3. Save the file to the AddressBook.API directory with a name of Program.cs.

  4. Open a system command prompt and change to the directory where the .csproj file is located.

  5. Build and run the application using the .NET CLI.

    dotnet build
dotnet run

    The use of build is not strictly necessary here since the run command will automatically perform a build if necessary.

Two directories that are created during the build process:

  • obj: Temporary files and intermediate artifacts used by the build system

  • bin: Output of the build process

If missing, both of these directories will be recreated by the build system. Therefore, it is recommended to not check these directories into source control (e.g., include them in the .gitignore file).

Each of these directories will have subdirectories based on the build configuration (Debug, Release) and the TFM of the project.

The default build configuration is Debug. The Release configuration enables several runtime performance optimizations and is used during the pre-deployment publish process. However, for testing purposes, it is also possible to specify the build configuration when using the build and run CLI commands.

dotnet build -c Release
dotnet run -c Release

Choosing the build configuration is possible via the menu/toolbar in IDEs such as Visual Studio and Rider.

An output directory within bin will include:

  • The compiled project assembly (.dll)

  • Any additional dependencies

  • Native executable file for the platform where the build was performed

  • File containing debug symbols (.pdb)

  • Runtime configuration file (*.runtimeconfig.json)

As seen earlier, the dotnet run command can be used without any parameters when executed in a directory that contains a project file. However, the path to the project file can also be provided as a parameter.

dotnet run --project ./AddressBook.API/AddressBook.API.csproj

In a non-development environment, the app is launched by providing the path to the compiled assembly.

dotnet AddressBook.API.dll

The .NET CLI is able to run the code in the assembly by using a platform-specific executable that is included with the runtime.

Host

One responsibility of the entry point function in an ASP.NET Core app is to create a host. The host is an object that encapsulates an app’s resources and lifetime functionality, such as:

  • Configuration

  • Logging

  • Dependency injection (DI)

  • App shutdown

The HostApplicationBuilder class can be used to build and configure a .NET Generic Host for any .NET project. However, in an ASP.NET Core web app, Microsoft recommends using WebApplicationBuilder to create a host with pre-configured default settings that are appropriate for a web app.

var builder = WebApplication.CreateBuilder();

The WebApplicationBuilder class has some useful properties that are initialized when the CreateBuilder method is called:

  • Environment: Provides information about the current web hosting environment

  • Services: Collection of application services that are available to be used via dependency injection

  • Configuration: Collection of configuration providers (used to read app settings)

  • Logging: Collection of logging providers (used to record log messages)

We will use all of these properties (and learn more about them) as we add more functionality to the app.

HTTP Server

In addition to initializing the properties listed above, the WebApplicationBuilder also configures ASP.NET Core’s built-in HTTP Server named Kestrel.

There are many options that can be configured for Kestrel, and we will change some of them later on. Right now, it is just important to know that Kestrel (by default) will listen for incoming HTTP requests on port 5000.

Request Processing Pipeline

After the WebApplicationBuilder has been configured, you call its Build method to create the WebApplication object.

var app = builder.Build();

The WebApplication is responsible for managing the request processing pipeline. To build a useful web app, we will need to add some components (referred to as middleware) to the pipeline. However, it is possible to run the app without any middleware. We just need to call the Run method of the WebApplication to complete the startup process and have Kestrel start listening for incoming requests.

app.Run();
Web Application

  1. Open Program.cs in your preferred text editor.

  2. Delete the existing code that prints out "Hello, World!".

  3. Add code to create a WebApplicationBuilder, create a WebApplication, and call Run.

    var builder = WebApplication.CreateBuilder(args);

var app = builder.Build();

app.Run();

  4. Save the changes to Program.cs.

  5. Use the .NET CLI to start the app.

    dotnet run

  6. Take note of two important lines in the console output:

    Now listening on: http://localhost:5000
Application started. Press Ctrl+C to shut down.

  7. Open your preferred web browser and make a request for http://localhost:5000 (the result will be a 404).

  8. Return to the console and take note of this line:

    Request reached the end of the middleware pipeline without being handled by application code.

    Based on what was just discussed regarding the request pipeline, this message should make sense.

  9. Press Ctrl+C in the console to shut down the app.
