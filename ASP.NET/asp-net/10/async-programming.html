Asynchronous Programming

With imperative code in C#, statements are executed synchronously. In other words, a statement cannot execute until the statement immediately before it has completed. This default behavior is a good thing since many statements depend on the work performed by previous statements. If every operation completed instantly, this wouldn’t present a problem. However, there are many occasions where it is desirable to perform an operation asynchronously and allow other work to be performed while a long-running operation is in progress.

For an interactive user interface, performing an operation asynchronously allows the UI to remain responsive. This allows the UI to provide some feedback about the operation (e.g., progress bar) and maybe an option to cancel the operation.

CPU-Bound vs. IO-Bound

There are two types of operations that can benefit from an asynchronous approach - CPU-bound and IO-bound. The difference involves why the operation could take a long time to complete.

For a CPU-bound operation, the operation could be completed faster if the operation could be broken down into smaller tasks that can be executed in parallel. The .NET Task Parallel Library (TPL) has types and APIs that can help with this type of scenario.

Task.WaitAll(task1, task2);

On the other hand, an IO-bound operation is when time must be spent waiting for input/output operations to be completed. Examples include reading from disk, accessing a database, or communicating over a network. One option for this type of scenario is to execute the operation on a separate thread and configure a delegate to be called when the operation completes (i.e, a callback). Unfortunately, this can often lead to code that is hard to follow and difficult to maintain.

Task Asynchronous Programming Model (TAP)

Although .NET has always provided the ability to work with threads and callbacks directly, it is rarely necessary and no longer recommended. Instead, the newer task asynchronous programming model (TAP) provides an abstraction over asynchronous code.

The core component of the TAP is the Task type that is used to model asynchronous operations. The Task type is supported by the async and await keywords to produce asynchronous code that is easier to read and maintain.

Using the TAP results in compiler generated code that uses threads and callbacks just like if you decided to write the code yourself using those low-level primitives.

For I/O-bound code, you await an operation that returns a Task inside of an async method.

public async Task<IActionResult> GetPeople()
{
    var people = await db.GetAllPeopleAsync();
    return Json(people);
}

When the thread executing this method reaches the await, the requested operation will be performed in the background and the executing thread will be released so that it can perform other work. Once the background work completes, the code after the await will execute (acts as the callback code).

In the case of a desktop app, the "other work" for the main thread would likely be to listen for other UI events (e.g., user clicking cancel).

In an ASP.NET Core app, the "other work" is the ability to respond to additional incoming requests. An ASP.NET Core app uses a pool of threads to handle incoming requests and the server will return an HTTP 503 (service unavailable) response if there are no threads available for handling a new incoming request. By allowing the request thread to return to the pool while waiting for an I/O operation to complete, the scalability of an app can be improved.

Making server-side actions asynchronous can improve server scalability. However, doing so does NOT change the experience for the end-user. To provide a good experience for the end-user, the code on the client-side should make the network call to the server in an asynchronous way (e.g. use the asynchronous fetch method in JavaScript).
Refactor to use async/await

  1. Within the GetAllCustomers endpoint, modify the LINQ query so that await is used with the ToListAsync method that returns a Task. This will initially result in a compiler error.

    var customers = await db.Customers
  .OrderBy(c => c.CustomerID)
  .Skip(offset).Take(limit)
  .ToListAsync();

    It is a standard convention within the framework for methods that return a Task to end with the suffix Async.

  2. Modify the definition of the GetAllCustomers action so that it is an async method that returns a Task type.

    public async Task<ActionResult<Customer[]>> GetAllCustomers(int offset = 0, int limit = 10)

  3. Run the app and test the endpoint.

    As discussed, there will not be a noticeable change in behavior but this approach will allow for more efficient use of server resources to improve the scalability of the app.

  4. If you would like, you can modify more of the endpoints to be asynchronous.

Background Tasks

Sometimes, it is desirable to have a long-running service that can periodically perform specific tasks. This can be useful for many use-cases:

  • Automatically perform maintenance tasks during times of low activity

  • Check for specific conditions that might require additional action (e.g., e-mail notification)

  • Execute tasks that have been added to a queue by other components

In ASP.NET Core, background tasks can be implemented as hosted services. A hosted service is a class with background task logic that implements the IHostedService interface.

public class TimedHostedService : IHostedService

The hosted service must implement two methods:

  • StartAsync: Contains the logic to start the background task. Common to use a timer to schedule a periodic task.

    public Task StartAsync(CancellationToken stoppingToken)
{
    _timer = new Timer(DoWork, null, TimeSpan.Zero,
        TimeSpan.FromSeconds(60));

    return Task.CompletedTask;
}

  • StopAsync: Executed when performing a graceful shutdown. Any active times should be stopped.

    public Task StopAsync(CancellationToken stoppingToken)
{
    _timer?.Change(Timeout.Infinite, 0);
    return Task.CompletedTask;
}

The AddHostedService method is used during app startup to register the hosted service.

services.AddHostedService<TimedHostedService>();
