Testing

Testing your code for accuracy and errors is at the core of good software development. Making the components of your app easier to test typically means a more loosely-coupled design and that tends to result in more flexible, maintainable software. Therefore, it is a recommended best practice to think about how to make your code more testable as you write it (even if you will never end up writing any automated tests).

  • Unit tests: Ensure that individual components work as expected

  • Integration tests: Ensure that component interactions work as expected against external artifacts like databases

  • Functional tests: Ensure the app works as expected from the user’s perspective

Unit Testing

Unit testing involves testing a part of an application in isolation from its infrastructure and dependencies. When you unit test controller logic, only the content of a single action or method is tested, not the behavior of its dependencies or of the framework itself.

When unit testing becoming difficult, the most common reason is poor dependency management. It is essential that a component can be tested independent of its dependencies or that a suitable replacement for a dependency can be provided during testing.

Implicit (or hidden) dependency
string GetGreeting(string name) {
    var now = DateTime.Now;
    if (now.Hour < 12) {
        return $"Good morning, {name}";
    ...
Explicit / injectable dependency
string GetGreeting(string name, DateTime? now = null) {
    now = (now ?? DateTime.Now);
    if (now.Value.Hour < 12) {
        return $"Good morning, {name}";
    ...

When testing controller actions, make sure you focus only on their behavior. A controller unit test avoids things like filters, routing, or model binding (the mapping of request data to a model or DTO). A well-written set of unit tests should be able to be run frequently without much overhead.

Unit Testing Frameworks

Unit tests are implemented by using a test framework. There are several different unit testing frameworks that can be used with ASP.NET Core. The most popular (and most frequency referenced in the documentation) is xUnit. The .NET SDK also includes project templates that are based on xUnit.

Unit test project

  1. In Visual Studio, select File  Add  New Project…​, select the "xUnit Test Project" template, and name the project Todo.Tests

  2. Add a project references to Todo.Tests for all of the other projects (Entities, DataAccess, and API)

Most unit testing frameworks use a collection of attributes to identify test methods. xUnit uses the Fact attribute to identify a test that should always be true and the Theory attribute is used to identify a test that should be true for a particular set of data.

[Fact]
public void PassingTest() {
    Assert.Equal(4, Add(2, 2));
}
[Theory]
[InlineData(3)]
[InlineData(5)]
[InlineData(6)]
public void MyFirstTheory(int value) {
    Assert.True(IsOdd(value));
}

The Visual Studio Test Explorer uses these attributes to populate its interface. The CLI also understands these attributes so that you can run your tests from the command-line or as part of a CI/CD pipeline.

dotnet test
Test summary: total: 1, failed: 0, succeeded: 1, skipped: 0, duration: 1.8s
Build succeeded in 5.4s

Stubs and Mocks

For an interface-based dependency, the unit test library can define an implementation that simulates the behavior of the "real" component. Depending on how it is used, this object might technically be defined as a stub or a mock.

  • Stub: Controllable replacement for a dependency that allows for testing of a component without having to deal with the dependency directly

  • Mock: Used to test how a component interacts with a dependency (a mock object will often decide whether a unit test has passed or failed)

Mock ITodoDb implementation

  1. Add a new class to the Todo.Tests project named TodoDbStub that implements ITodoDb

    using Todo.Entities;

namespace Todo.Tests;

internal class TodoDbStub : ITodoDb
{
}

  2. Use the pop-up in Visual Studio to implement the methods of the interface.

  3. Within the class, define a static list of test to-do items.

    private static List<TodoItem> _todos = new List<TodoItem> {
    new TodoItem { Id = 1, Name = "One", IsComplete = false },
    new TodoItem { Id = 2, Name = "Two", IsComplete = true }
};

  4. Implement the GetTodo method using the static test data.

    public async Task<TodoItem?> GetTodo(int id)
{
    return await Task.Run(() =>
        _todos.SingleOrDefault(t => t.Id == id));
}

    We cannot query the static list asynchronously. However, we would like the method to behave in a manner as close as possible to the "real" component. Therefore, we use a task to call the synchronous LINQ method.

Arrange, Act, Assert

A unit test can typically be divided into three parts:

  • Arrange: Create and configure the object under test (including any required dependencies)

  • Act: Perform the action being tested

  • Assert: Check the result of the action against a prediction

Some developers like to explicitly identify these parts when writing tests to help with readability and maintainability.

Test retrieval of a to-do

We are going to use the existing Test1 method but feel free to rename the class and method if you would like.

  1. Since we will be calling an async controller action, modify the Test1 method to be async

    public async Task Test1()

  2. Within the Test1 method, create an Arrange-Act-Assert structure

    [Fact]
public async Task Test1()
{
    // Arrange

    // Act

    // Assert
}

  3. For the "Arrange" code, create a TodoDbStub and an instance of TodoController

    var db = new TodoDbStub();
var controller = new TodoController(db);

  4. For the "Act" code, call the GetTodo action.

    var r = await controller.GetTodo(2);

    For the "Assert" portion, we should check the type of result returned and then dig into the result to verify that the correct to-do item was actually returned.

  5. Add some code for the "Assert" portion.

    Assert.NotNull(r.Result);
Assert.IsAssignableFrom<OkObjectResult>(r.Result);
OkObjectResult objResult = (OkObjectResult)r.Result;
Assert.NotNull(objResult.Value);
Assert.IsAssignableFrom<TodoItem>(objResult.Value);
TodoItem item = (TodoItem)objResult.Value;
Assert.Equal(2, item.Id);

  6. From the Visual Studio menu, select Test  Run All Tests and confirm that the test passes.

  7. Change the expected Id value and confirm that the test fails.

  8. Change the expected Id back to the correct value.

  9. Open a command prompt and run the test using the CLI (you will need to be in the same directory as the Todo.Tests project file).

    dotnet test

Integration Testing

While unit testing is useful for testing components in isolation, integration testing ensures that an app’s components function correctly when used together.

The Microsoft.AspNetCore.Mvc.Testing NuGet package includes the TestServer and WebApplicationFactory components that will be useful when implementing automated integration tests.

When using TestServer as a test web host, the host will need access to the implicitly defined Program class in the web app. This is so the test web host can run the app’s startup code that configures the app’s services and constructs the request pipeline. There are two methods that can be used to make the Program class visible to the test project.

  1. Use an InternalsVisibleTo element in the web app’s project file

    <ItemGroup>
     <InternalsVisibleTo Include="Todo.Tests" />
</ItemGroup>

  2. Use a partial class declaration to cause the Program class to be defined as public instead of internal

    public partial class Program { }

    A third option would be to not use top-level statements. In that scenario, you can simply change the access modifier on the Program class from internal to public.
Test web host

  1. In the Todo.API project, add a partial class declaration to the bottom of Program.cs

    public partial class Program { }

  2. Add the Microsoft.AspNetCore.Mvc.Testing NuGet package to the Todo.Tests project.

  3. Add a new class to the Todo.Tests project named IntTest1

    public class IntTest1(WebApplicationFactory<Program> factory)
    : IClassFixture<WebApplicationFactory<Program>> {

}

    This will provide us with a WebApplicationFactory object that we can use to obtain an HTTP client for making requests.

  4. Within the class, define a new test that checks the status code and content type for the two GET endpoints.

    [Theory]
[InlineData("/todoitems")]
[InlineData("/todoitems/1")]
public async Task Get_SuccessAndContentType(string url)
{
    // Arrange
    var client = factory.CreateClient();

    // Act
    var response = await client.GetAsync(url);

    // Assert
    response.EnsureSuccessStatusCode(); // Status Code 200-299
    Assert.Equal("application/json; charset=utf-8",
        response.Content.Headers.ContentType?.ToString());
}

  5. Run the test and confirm that is passes (if your database has a Todo with an id of 1).

There are many ways that WebApplicationFactory and the test web host can be customized to accomodate different testing use-cases. Refer to the documentation for more information.
