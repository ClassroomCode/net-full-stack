Error Handling

For any app, proper error handling is essential. In a development/staging environment, having a good error handling system can help with identifying and fixing bugs. In production, solid error handling is important for system visibility, the client experience, and security.

Some general best practices for error handling include:

  • Handle errors as best you can when they occur

  • Record error information and/or send a notification

  • Provide the user with an appropriate response

    When returning a response for an error, do not reveal sensitive information that a malicious actor could potentially use against you (e.g., database schema information). This is one form of a common security vulnerability known as sensitive data exposure.

Developer Exception Page

When running in a development environment, it is helpful to have as much information about the error as possible. The DeveloperExceptionPage middleware can be used to capture exceptions from the pipeline and generate a detailed error response that includes:

  • Stack trace

  • Query parameters

  • Headers

  • Endpoint metadata

For a request that includes an Accept header of text/html, the response will be HTML. Otherwise, the request will be sent in plain text.

Detailed errors

  1. Add the DeveloperExceptionPage middleware to the pipeline of the API project (this should be the first piece of middleware - immediately after the call to builder.Build).

    if (app.Environment.IsDevelopment()) {
  app.UseDeveloperExceptionPage();
}

  2. For testing purposes, modify the database connection string in Program.cs so that the database name is incorrect.

  3. In Visual Studio, select Debug  Start Without Debugging

    If running with debugging, the exception would get caught by the Visual Studio exception assistant.

  4. Invoke the endpoint to retrieve all of the customers and examine the response.

  5. Use the console window to stop the app (leave the error in the connection string for the next exercise).

Exception Handling Middleware

In a non-development environment, you definitely do not want to return the developer exception page. Instead, you can use the ExceptionHandler middleware to produce an error payload and the Problem helper method can be used to generate an RFC 7807 compliant payload.

Exceptions in production

  1. Extend the code in Program.cs to use the exception handling middleware when the app in not running in a development environment.

    if (app.Environment.IsDevelopment()) {
  app.UseDeveloperExceptionPage();
}
else {
  app.UseExceptionHandler(app => {
    app.Run(async context => {
      await Results.Problem("An unexpected error occurred.").ExecuteAsync(context);
    });
  });
}

    Instead of providing a request delegate to the UseExceptionHandler method, you could instead provide a route (e.g., "/error") and then implement that route with a controller action.

  2. Modify launchsettings.json so the app will think it is running in a production environment.

    "ASPNETCORE_ENVIRONMENT": "Production"

  3. Run the app without the debugger, invoke an endpoint, and check the response.

  4. Use the console window to stop the app, change the environment back to "Development", and fix the database connection string.
