Controllers

Rather than defining endpoints with function-based handlers (in the style used by minimal APIs), it is also possible to take a Model-View-Controller (MVC) approach and use controllers to handle incoming requests.

A method of a controller with a route defined that can be executed via an HTTP request is referred to as a controller action.

Responsibilities

The responsibility of a controller action is to generate an appropriate response for an incoming request. To fulfill that responsibility, a controller action will often:

  • Perform input validation on the incoming request data

  • Perform function-level access control (authorization)

  • Retrieve and/or modify model object(s)

  • Choose the format for the response body: JSON, HTML, XML, etc.

Requirements

  • A collection of built-in services must be added to support the use of controllers

    builder.Services.AddControllers();

  • Middleware must be added to create endpoints for routing attributes that are used within a controller

    app.MapControllers();

  • Controller must be defined as public

  • Controller must have a name that ends with Controller or inherit from a class that ends with Controller

  • Routing endpoint(s) must be defined for mapping incoming requests to controller actions

Controller support

  1. In Program.cs, add the required services to support the use of controllers.

    builder.Services.AddControllers();

  2. Immediately before app.Run(), add the middleware to create endpoints for any routes defined within controllers.

    app.MapControllers();

  3. Comment-out the two existing Minimal API endpoints.

Conventions

Although not requirements, there are several common conventions used when defining controllers in an ASP.NET Core app:

  • Place all controllers in a subfolder (and namespace) named Controllers

  • Inherit from Controller or ControllerBase (to make available many useful properties and methods)

    ControllerBase includes all the basic functionality that is useful for an API controller. The Controller class inherits from ControllerBase and includes additional functionality specifically to support the use of HTML views.

  • Use the ApiController attribute to enable some API-specific behaviors

    [ApiController]
public class CustomerController : ControllerBase

    Refer to the documentation to learn more about which specific behaviors are enabled by the ApiController attribute.

Return Types

There are several different options for what to use as the return type for a controller action.

Specific Type

It is possible to directly return a concrete type from a controller action. In this case (as we have seen previously), the system will automatically transform the type into a JSON response.

public List<Customer> GetAllCustomers()

Using List or IEnumerable as the return type will cause ASP.NET Core to buffer the result before writing it to the response. Alternatively, IAsyncEnumerator can be used to potentially stream the results to the client. Refer to the documentation for more information.

In some cases, using a specific type may be sufficient. However, a critical limitation with this approach is the inability to return a different type when the need arises (e.g., validation error).

IActionResult

The IActionResult type can be used to return various HTTP status codes. Convenience methods provided by ControllerBase can be used for generating an appropriate response.

public IActionResult GetCustomer(string id) {
    // other code
    return customer is null ? NotFound() : Ok(customer);
}

One downside of using IActionResult is that it’s not clear from the method signature what specific types this action might return.

ActionResult<T>

Another alternative for web API controller actions is to use the generic ActionResult<T> type. This is now the recommended pattern to follow.

public ActionResult<Customer> GetCustomer(string id) {
    // other code
    return product is null ? NotFound() : todo;
}

There are some additional return types that you can use with a controller action, but they tend to be much less common than those just described. Refer to the documentation for more information.
Refactor to use a controller

  1. Add a new folder to the AddressBook.API project named Controllers

  2. Right-click on the Controllers folder, select Add  Class…​, and name the class CustomerController

    Instead of Add  Class…​, we could have used Add  Controller…​ but that would have added some extra things that we are going to add manually.

  3. Modify the class to inherit from ControllerBase and add the ApiController attribute.

    [ApiController]
public class CustomerController : ControllerBase
{
}

  4. Add a controller action for each of the existing endpoints.

    [HttpGet("customer")]
public ActionResult GetAllCustomers() {
    using var db = new NorthwindContext();
    var customers = db.Customers.ToList();
    return Ok(customers);
}

[HttpGet("customer/{id}")]
public ActionResult GetCustomer(string id) {
    using var db = new NorthwindContext();
    var customer = db.Customers.Find(id);
    if (customer is null) return NotFound();
    return Ok(customer);
}

    The code above uses an attribute on each action to define a route but the route template string works the same as it does in Minimal APIs (constraints, etc.)

  5. Run the app and use the .http file to confirm that all of the endpoints work the same as they did before.
