Dependency Injection

In the AddressBook project right now, each endpoint creates an instance of the NorthwindContext concrete type. This approach is not flexible and can end up becoming difficult to maintain and test.

ASP.NET Core includes built-in support for dependency injection (DI) which is a technique for achieving Inversion of Control (IoC) between components and their dependencies.

Service Lifetime

For a component that is registered with DI, the system will be responsible for managing the lifetime of the component. One aspect of this is that when an instance is required, the system will need to know if an existing instance of a component can be reused or if a new instance should be created. Therefore, when registering a component with DI, s specific lifetime policy must be specified:

  • Singleton: Only one instance of the component will be created. This single instance well be reused whenever an instance of the component is required.

  • Transient: A new instance of the component will be created whenever an instance of the component is required.

  • Scoped: When a new request arrives, a new scope is created and the scope ends when a response is returned for that request. This allows for a single instance of a component to be reused if needed multiple times during the processing of a request.

    For the majority of components in an ASP.NET Core app, the Scoped lifetime is the correct choice. A different lifetime should only be used when there is a clear reason to do so.

Service Registration

Components that will be used via dependency injection are added to WebApplicationBuilder’s Services collection during app start up.

A service can be registered as a concrete type:

builder.Services.AddScoped<NorthwindContext>();

In this example, whenever the system needs to call a method that accepts a parameter of the NorthwindContext type, an instance will be passed in. The DI system will follow the rules of the scoped lifetime policy to decide if a new instance needs to be created or an existing instance can be reused.

Refactor to use DI

  1. In Program.cs, register the NorthwindContext type as a scoped service. Instead of using AddScoped, use the AddDbContext method that is specifically designed for a DbContext types and provide the connection string.

    builder.Services.AddDbContext<NorthwindContext>(options =>
  options.UseSqlServer(@"Server=localhost;Database=Northwind;Integrated Security=True;TrustServerCertificate=True"));

  2. Remove the OnConfiguring method from NorthwindContext and add a constructor that accepts DbContextOptions and calls the base class constructor.

    public NorthwindContext(DbContextOptions<NorthwindContext> options)
  : base(options) { }

    This sets up the context to be used via dependency injection but the controller must also be modified to receive it.

Explicit Dependencies Principle

It is a recommended best practice for controllers to adhere to the Explicit Dependencies Principle. This means that every controller should include all of its required dependencies as required constructor parameters. This allows for those dependencies to be provided via dependency injection or passed in explicitly for unit testing.

A traditional constructor can be used to receive the dependency and retain it for use by other controller methods:

public class CustomerController : ControllerBase
{
    private NorthwindContext _db;

    public CustomerController(NorthwindContext db) {
        _db = db;
    }
}

Alternatively, C#'s newer primary constructor syntax can be used to accomplish the same goal.

Leverage DI

  1. Add a primary constructor for the CustomerController class that accepts a NorthwindContext

    public class CustomerController(NorthwindContext db) : ControllerBase

  2. Delete the using statement from each action (since db will now be a class-level variable provided via the constructor).

  3. Run the app and test the endpoints. Everything should work as before.

Dependency Inversion

The Dependency Inversion Principle states that high level modules should not depend on low level modules; both should depend on abstractions. To support this principle, it is possible to define a service as an implementation of an interface and register the interface with the DI system.

builder.Services.AddScoped<IRepository, MyRepository>();

In this example, service consumers can be programmed to work with any implementation of IRepository. The DI system will pass in an implementation of the MyRepository concrete type at runtime. However, in other contexts (e.g., unit tests), an alternative implementation of IRepository (e.g., mock object) can be used instead.

Program to interfaces, not implementations
— Design Patterns: Elements of Reusable Object-Oriented Software

We could define an interface with methods for all of the ways we intend to work with the data and then modify NorthwindContext to implement that interface. This would require more effort but would enable us to completely encapsulate the fact that we are using EF Core. However, wrapping EF Core with a generic repository can hide powerful features like IQueryable for dynamic querying.
