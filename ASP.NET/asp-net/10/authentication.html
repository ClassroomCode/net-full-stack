Authentication

In any authentication scheme (web UI, REST API, airport security checkpoint, etc.), there are two fundamental aspects:

  1. Discover the identity of an entity through an identifier

    • Who are you claiming to be?

  2. Verify the identity by validating credentials provided by the entity

    • Why should I believe you?

An identifier can be a username, e-mail address, access key id, or something else that can be used to uniquely identify the entity. The identifier is not considered to be sensitive data.

Credentials come in many different forms. In every case though, the credentials provided by an entity must be able to provide a level of confidence regarding the identity of the entity. The simplest form of credential is a password since it’s something that only the entity should be able to provide. A password is sensitive data that must be protected when stored or transmitted.

For a Web app, the incoming request must contain something that can be used to serve as the identifier and the credentials.

HTTP Authentication

RFC 7235 defines a general HTTP authentication framework. This framework describes how a server can challenge a client (HTTP 401) and how a client can provide authentication information via the Authorization header. This general framework forms the foundation for several specific authentication schemes. Some popular schemes include:

  • Basic

  • Digest

  • API Key

  • Bearer Token

  • AWS4-HMAC-SHA256 (scheme used by AWS)

HTTP Basic Authentication

The "Basic" HTTP authentication scheme is defined in RFC 7617. With this scheme, an identifier (user ID) and credential (password) are sent with every request. The two values are concatenated together to form a single value (using the ":" character as a delimiter), Base64 encoded, and sent as the value of the Authorization header.

Since the credential is sent in clear text (encoded but not encrypted), it is critical that the Authorization header only be sent over a connection that is secured with transport level security (HTTPS/TLS).

An advantage of this scheme is the simplicity of its implementation. Any type of client app should be able to send the required Authorization header.

One disadvantage of this scheme is the need to re-validate the client credential for every request. In the case of a web UI, a cookie is often used to send a temporary authentication "ticket" that is sent with subsequent requests and used to match the client up with a user session object that is maintained in server memory.

HTTP Digest Authentication

The Digest authentication scheme was originally developed as an alternative to the Basic authentication scheme that could be used over an insecure connection (HTTP). To achieve this, the Digest scheme uses the same Authorization header as the Basic scheme but applies a hash function to the header value before sending it over the network.

Although some enhancements have been made to the Digest scheme over the years, it is rarely used today. The main reason for this is the more prevalent use of HTTPS. The additional complexity of the Digest scheme (when compared to the Basic scheme) is not beneficial when using HTTPS.

API Key Authentication

Used by many modern APIs, an "API Key" authentication scheme is similar to the Basic authentication scheme. A large randomly generated string is provided to the client in advance and that string serves as both the identifier and the credential.

Since the API key serves as the credential, it is sensitive and needs to be protected in the same way that a password would be. Like passwords, API keys should be rotated on a regular basis.

Using an API key works well for securing back-end APIs and for APIs that do not utilize function-level access control. However, like with the Basic scheme, the API key will likely have to be validated against a back-end data source as part of the processing of each request.

Some developers implement their API so that the API key is sent as part of the URL or via a custom header. However, it is a recommended best practice to use the standard HTTP Authorization header.

Bearer Token Authentication

RFC 6750 describes a scheme that uses bearer tokens to access OAuth 2.0 protected resources. This scheme is similar to the previous schemes in that a string is still sent in the Authorization header that serves as the identifier and the credential. What makes the Bearer scheme unique is the format of that string.

With this scheme, the value of the Authorization header is a security token that was issued by an authorization server. Much like a physical passport, a token contains a collection of claims (name, birthdate, etc.) and a way to verify that the token is genuine. By saying that a token is "genuine", it means we have a way to verify that the token:

  • Was issued by a known authority that we trust

  • Has not been altered since it was issued

If both of these things can be confirmed then the claims contained within the token can be trusted without the need to communicate with the issuing authority.

The most common way to format a bearer token is as a JSON Web Token (JWT). A JWT consists of three parts:

  • Header: Specifies the type of the token and the signing algorithm being used

    {
  "alg": "HS256",
  "typ": "JWT"
}

  • Payload: Contains the claims. Claims are key-value pairs and can be anything. However, there are some predefined claims that should be included to promote interoperability.

    • iss: Issuer (identifies the principal that issued the JWT)

    • exp: Expiration time (numeric unix timestamp value)

    • sub: Subject (claims are statements about the subject)

    • aud: Audience (principal intended to process the JWT)

  • Signature: Generated using the header, payload, and a client secret. The integrity of the token can be verified on the server by regenerating the signature with data from the incoming token and the same client secret.

    In the case of a 3rd-party authentication provider like Google or Facebook, the secret is provided when registering your app with the provider.

JWT Generation

In many scenarios, your API will not responsible for generating a JWT. Instead, the API will only need to verify a JWT that was issued by a separate authentication server. In the case of our AddressBook app, the API will act as both the authentication server and the client app.

Authentication controller

  1. Add the NuGet package named Microsoft.AspNetCore.Authentication.JwtBearer to the AddressBook.API project.

  2. Add a new folder to the project named Auth

  3. Add a C# class to the Auth folder named TokenProvider with a method named Create that takes a user e-mail and returns a token as a string.

    public class TokenProvider
{
  public string Create(string userEmail) {
    //
  }
}

  4. Within the Create method, define a variable for the client secret that will be used when generating the JWT.

    var clientSecret = "randomly-generated-client-secret";

    The client secret should be randomly generated (minimum of 32 bytes for SHA-256) and should be considered sensitive. Therefore, this secret should not be stored in the source code. We will move this secret to a better location when we discuss the configuration system in a future section.

  5. Add code to create a symmetric security key from the secret string and then use the key to create a signing credentials object.

    var securityKey = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(clientSecret));
var credentials = new SigningCredentials(securityKey, SecurityAlgorithms.HmacSha256);

  6. Finally, add the necessary code to generate and return a JWT.

    var tokenDescriptor = new SecurityTokenDescriptor {
  Subject = new ClaimsIdentity([
    new Claim(JwtRegisteredClaimNames.Sub, userEmail),
  ]),
  Expires = DateTime.UtcNow.AddMinutes(60),
  SigningCredentials = credentials,
  Issuer = "localhost:5000",
  Audience = "localhost:5000"
};
var handler = new JsonWebTokenHandler();
string token = handler.CreateToken(tokenDescriptor);
return token;

  7. So that the TokenProvider type can be used via dependency injection, register it as a service in Program.cs

    builder.Services.AddSingleton<TokenProvider>();

    The TokenProvider type is registered as a singleton service since it is a stateless helper class. This is the best fit but a different service lifetime would also work.

  8. Add a new controller to the Auth folder named AuthController that accepts a TokenProvider via a primary constructor.

    [ApiController]
public class AuthController(TokenProvider tokenProvider) : ControllerBase
{
}

    Instead of the Auth folder, it would be okay to add the controller to the Controllers folder if desired.

  9. Within the AuthController class, define a type that represents the data we will be expecting to receive in the login action.

    public class LoginPayload {
  public string? Email { get; set; }
  public string? Password { get; set; }
}

  10. Add an endpoint to AuthController that exchanges a username and password for a JWT.

    [HttpPost("auth/login")]
public ActionResult<string> Login(LoginPayload user) {
  // TODO: validate the user information against a back-end datastore
  if (user.Email is null || user.Password != "abc123") return Unauthorized();
  var token = tokenProvider.Create(user.Email);
  return Ok(token);
}

    It is a security best practice to use POST as the HTTP method for an endpoint like this since data sent in a request body will not be cached, bookmarked, or stored in browser history.

  11. Test this endpoint. If successful, the endpoint should return a Base64URL encoded JWT.

    POST http://localhost:5000/auth/login
Content-Type: application/json
{
  "email": "bill@example.com",
  "password": "abc123"
}

Authentication Service and Middleware

ASP.NET Core includes an authentication service (IAuthenticationService) and authentication middleware. The middleware obtains the authentication data from the incoming request and passes it to the authentication service that uses registered authentication handlers to set the authenticated user.

JWT authentication handler

  1. Configure the authentication service and the JWT handler.

    builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
  .AddJwtBearer(options => {
    options.RequireHttpsMetadata = false;
    options.TokenValidationParameters = new TokenValidationParameters {
      IssuerSigningKey = new SymmetricSecurityKey(
        Encoding.UTF8.GetBytes("randomly-generated-client-secret")),
      ValidIssuer = "localhost:5000",
      ValidAudience = "localhost:5000"
    };
  });

    For a complete list of the available options for the AddJwtBearer method, refer to the documentation. The client secret appears again here. As mentioned earlier, this will be moved into a better location later on.

  2. Add the authentication middleware to the request pipeline. This must appear before any middleware that may need information about the authenticated user (e.g. MapControllers).

    app.UseAuthentication();

  3. Build the solution and check for any compiler errors.

    Although all the pieces are now in place to support JWT-based authentication, authorization must still be configured to secure access to the API’s endpoints.
