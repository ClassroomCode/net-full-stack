Configuration

It is often desirable to keep some app settings separate from the compiled source code. This makes those settings easier to maintain and allows them to be changed without the need to modify, re-compile, and re-deploy the code. Common examples include:

  • External service URLs

  • Database connection strings

  • API keys

  • Logging / notification settings

  • Settings that differ based on the hosting environment (development, staging, production)

Sources and Providers

Fundamentally, app configuration information is just a collection of key-value pairs. A configuration source represents a location where some key-value pairs come from. ASP.NET Core includes built-in support for a wide variety of configuration sources:

  • Files, such as appsettings.json

    {
  "MySetting": "MyValue"
}

  • System environment variables

  • Command-line arguments

    dotnet EComm.API.dll MySetting=MyValue

  • In-memory .NET objects

  • User secrets

  • Azure Key Vault

  • Azure App Configuration

In addition to these, there is also support for custom configuration providers. AWS, for example, offers a custom provider for using the AWS Secrets Manager.

When using WebApplicationBuilder, settings are read from the following sources by default (highest to lowest priority):

  1. Command-line arguments

  2. System environment variables

  3. User secrets

  4. appsettings.{Environment}.json (e.g., appsettings.Development.json)

  5. appsettings.json

If a value with the same key is read from multiple configuration sources, the one with the highest priority will take precedence.

Because of the behavior described above, it can be helpful to think of appsettings.json as defining the "default" or "fallback" settings for an app.

Setting can be nested:

{
  "Inventory": {
    "ApiKey" : "1234"
  }
}

For the example above…​

  • Refer to the value for ApiKey in code and at the command line by using the entire path with a colon as the separator: Inventory:ApiKey

  • To override the value of ApiKey with an environment variable, use the entire path with two underscores as the separator: Inventory__ApiKey

It is possible to specify a custom prefix for environment variables.

builder.Configuration.AddEnvironmentVariables(prefix: "MyApp_");

This allows you to use a more descriptive name for the environment variable (MyApp_MySetting) while still referring to the value in code the same way (MySetting).

Dependency Injection

The recommended way for controllers (and other services) to access configuration settings at runtime is via dependency injection and the IConfiguration service. This service is configured automatically by WebApplicationBuilder.

public class ProductController(IConfiguration configuration)
    : ControllerBase
{
    public ActionResult GetProducts()
    {
      var apiKey = configuration["MySetting"];
      ...
    }
}

In this example, we are injecting the entire IConfiguration object and accessing values based on a string key. An alternative approach would be to inject a strongly-typed object that only includes settings that are relevant for the receiver. Doing so would require more effort, but it might be attractive for a more complex app that has a large collection of configuration settings. For more information, refer to the documentation for information about the options pattern.
Refactor app settings

There are several items in the AddressBook.API project that should not be hard-coded into the C#. These items include the database connection string and the JWT configuration.

  1. Right-click on the AddressBook.API project, select Add  New Item…​, and use a file name of appsettings.json

  2. Add a setting for the database connection string and copy-paste the value from Program.cs

    {
  "ConnectionStrings": {
    "Northwind": "connection string here"
  }
}

  3. In Program.cs, retrieve the connection string from the configuration systems and use it when calling UseSqlServer

    var connStr = builder.Configuration.GetConnectionString("Northwind");
builder.Services.AddDbContext<NorthwindContext>(options =>
    options.UseSqlServer(connStr));

  4. Run the app and test and endpoint to confirm that everything still functions as before.

  5. Stop the app and add another section to appsettings.json for the JWT-related settings.

    "Jwt": {
  "ClientSecret": "",
  "Issuer": "",
  "Audience": "",
  "ExpirationInMinutes": ""
}

  6. Copy the settings from TokenProvider and paste them into appsettings.json

    "Jwt": {
  "ClientSecret": "randomly-generated-client-secret",
  "Issuer": "localhost:5000",
  "Audience": "localhost:5000",
  "ExpirationInMinutes": "60"
}

  7. Modify TokenProvider to that it accepts an IConfiguration via a primary constructor.

    public class TokenProvider(IConfiguration config)

    This object will automatically be provided by the DI system when it creates an instance of TokenProvider

  8. Modify the Create method of TokenProvider so that it reads the information it needs from the configuration system.

    var clientSecret = config["Jwt:ClientSecret"]!;
...
Expires = DateTime.UtcNow.AddMinutes(int.Parse(config["Jwt:ExpirationInMinutes"]!)),
...
Issuer = config["Jwt:Issuer"]!,
Audience = config["Jwt:Audience"]!

    The null forgiving operator (!) is used in each case since the configuration system returns a nullable string (string?) for each setting. As an alternative, you could write code to check for the presence of each setting before using them.

  9. Modify the configuration of the authentication service in Program.cs in a similar way.

    IssuerSigningKey = new SymmetricSecurityKey(
  Encoding.UTF8.GetBytes(builder.Configuration["Jwt:ClientSecret"]!)),
ValidIssuer = builder.Configuration["Jwt:Issuer"]!,
ValidAudience = builder.Configuration["Jwt:Audience"]!

  10. Run the app and test the login endpoint.

User Secrets

When using appsettings.json and appsettings.{Environment}.json, those files are stored within the project directory structure. This means they will naturally end up the source control repository. This can be an issue if those file contain sensitive information such as database account passwords and API keys.

The Secret Manager is used during development for storing app secrets in a separate file (secrets.json) that is located outside of the project tree. The secrets file is in the same format as a standard appsettings.json file.

The Secret Manager tool is provided as part of the SDK for use during development. It is not intended to be used in a production environment. For non-development environments, a different configuration source should be used (e.g., system environment variables, key vault, etc.)

To enable user secrets for a project, the project file must contain a UserSecretsId property that is set to a UUID. The UUID is used by the Secret Manager as the name of the directory where the secrets.json file will be located. The init CLI command can be used generate the UserSecretsId property.

dotnet user-secrets init
<UserSecretsId>79a3edd0-2092-40a2-a04d-dcb46d5ca9ed</UserSecretsId>

You can also use the Secret Manager tool from within Visual Studio by right-clicking on the project and selecting Manage User Secrets. This will invoke the init command (if needed) and open the secrets.json file for editing.

The secrets file is located in the local machine’s user profile folder. You can edit this file directly, but Microsoft considers the location of the file to be an internal implementation detail that might change in the future.

  • Windows: %APPDATA%\Microsoft\UserSecrets\<user_secrets_id>\secrets.json.

  • macOS and Linux: ~/.microsoft/usersecrets/<user_secrets_id>/secrets.json

To set a secret, you can edit the secrets.json file, or you can use the set and remove CLI commands.

dotnet user-secrets set "Inventory:ApiKey" "1234"
dotnet user-secrets remove "Inventory:ApiKey"

A batch of secrets can be set by piping JSON to the set command.

  • Windows: type .\input.json | dotnet user-secrets set

  • macOS and Linux: cat ./input.json | dotnet user-secrets set
